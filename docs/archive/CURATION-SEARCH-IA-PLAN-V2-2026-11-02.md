## 1. 精选：一套机制，两处出口

### 1.1 先解决「两处精选重复」

现在的重复是这样来的：

- 首页主卡：一篇
- 首页「精选内容」栏：3 个项目（其实是项目清单，跟精选无关）
- 文字页「精选摘录」：3-4 篇文章

也就是说，**有三处自称精选，其中两处在讲文字，彼此不知道对方存在**。

本版的做法：**全站只有一个精选池（Curation Pool）**。

```
        ┌──────────── 精选池（按分数排名） ────────────┐
        │  第1位   第2位   第3位   第4位   第5位 …     │
        └────┬──────────────────┬──────────────────────┘
             │                  │
        首页主卡            文字页精选摘录
      （只放第 1 位）      （放第 2-4 位，见决策 D1）
```

两处不再各自评选，而是同一个榜的两个展示位。这样：

- 语义上只有一个「精选」，不构成精选通胀；
- 首页那位是当期主推，文字页那几位是荣誉榜，**天然不重复**（因为文字页从第 2 位开始取）；
- 一处变动，另一处跟着变，不会出现「首页推 A、摘录也推 A」的撞车。

### 1.2 机制：三道闸

这是本版的核心。主人要的是「有波动，但不是来一篇顶一篇」，用三道闸实现。

#### 闸一 · 准入（有没有资格参评）

一篇文章要进池子，必须同时满足：

1. 正文去掉空白与标点后 ≥ **800 字**（现行门槛是 40 字，形同虚设）；
2. 不是「正文只是标题重敲一遍」的空壳（现有判定保留）；
3. 有分类。

不满足就**不进池**，连参评资格都没有。这一闸挡掉「随手发一句」。

#### 闸二 · 计分（排第几）

| 项 | 代号 | 取值 | 谁来定 |
|---|---|---|---|
| 编辑定级 | E | 0 / 1 / 2 | 后台勾「精选」= 1；另有「置顶推荐」= 2 |
| 篇幅 | L | 0-3（800–2000 / 2000–4000 / 4000–8000 / >8000 字） | 现算 |
| 新鲜度 | T | 3 / 2 / 1 / 0（≤3 月 / ≤6 月 / ≤12 月 / 更久） | 现算 |
| 完成度 | C | 0 / 1（有分类 + 有标签 + 有封面，三者齐才给 1） | 现算 |

**总分 = E×3 + L + T + C，满分 3×3+3+3+1 = 16 分。**

设计取舍要说清：

- **E 权重最高（×3）**，因为这是个人站，编辑意志必须能压过算法。一个人写了 8000 字的流水账，不该只因为长就顶掉一篇 3000 字的真东西。
- **篇幅封顶 3 分**，防止「越长越赢」变成新的机械规则。
- **新鲜度不归零**，老文章最多掉 3 分，不会因为「放旧了」就崩盘——好的东西过两年还是好的。

#### 闸三 · 顶替（能不能上位）

这是防抖的关键，也是主人那句「必须有一个合理的理由」的落点。

> **挑战者总分必须比在位者高出 ≥ 2 分，才能顶替。差 1 分或 0 分，在位者继续在位。**

举例：

| 场景 | 计分 | 结果 |
|---|---|---|
| 现任 12 分，新文章 E=1、L=2、T=3、C=1 = 9 分 | 9 < 12 | **顶不动**，现任继续 |
| 现任 12 分，新文章 E=2、L=3、T=3、C=1 = 13 分 | 13 − 12 = 1 | **仍顶不动**（差 1 分，在位优势） |
| 现任 12 分，新文章 E=2、L=3、T=3、C=1，且现任已放旧到 T=1 → 现任 10 分 | 13 − 10 = 3 | **顶掉** |
| 现任 12 分，新文章勾了置顶 E=2、篇幅够、结构全 = 13，且现任同期 | 差 1 | 顶不动 |

所以「顶掉」这件事需要两件事同时发生：**新文章确实够格**，**或者现任自己掉分**（放旧）。这就是「合理的理由」。

反过来说，「来一篇新的就顶掉」在闸三下不可能发生：新文章刚发布，E 默认 0（没勾精选）、C 可能不齐，光靠 T=3 顶天拿 6 分，顶不动任何在池里的人。

### 1.3 波动从哪来（三种合法波动）

1. **编辑钦定**：主人勾了「精选」或「置顶推荐」，分数直接上一个台阶。
2. **在位衰减**：现任放满 3 个月后 T 从 3 降到 2，再 3 个月降到 1，自己让位。
3. **强作品出现**：新文够长、结构齐、又勾了精选，一次拿到 13 分以上。

三种波动都是可解释的，没有「随机」「按时间轮」这类说不清的东西。

### 1.4 可解释性：评选台账

构建时输出一份台账（落在项目根 `_curation-log.json`，不进 `public/`，不上线）：

```json
{
  "generatedAt": "2026-11-02",
  "slots": {
    "hero": { "slug": "metro-vs-gdp-rank-mismatch", "score": 11,
              "breakdown": { "E": 1, "L": 3, "T": 3, "C": 1 } },
    "picks": [ { "slug": "date-becomes-machine-string", "score": 9 }, ... ]
  },
  "history": [
    { "slug": "metro-vs-gdp-rank-mismatch", "replaced": "empty-card-and-latest-post",
      "margin": 2, "reason": "编辑标记 + 篇幅档 3 + 完成度齐" }
  ]
}
```

任何一次主卡换人，台账里都能查到「谁顶了谁、差几分、为什么」。这是「有理由」的物证。

页面上的呈现（文案待定，见决策 D2）：

- 主卡 meta 行：真入选写 `FEATURED`，兜底（池子为空时取最新）写 `LATEST`——这一点主人已认可。
- 可选：主卡下方加一行「入选理由」，一句话，由台账现算生成，不手写。

### 1.5 首页下方那栏怎么办

主人否掉了「改名项目」和「多类型混排」。本版建议：**撤掉这一栏**。

理由：

1. 首屏内容墙里已经有「项目」入口格，点进去就是 `/projects/`，那里才是项目该待的地方；
2. 首页保留三个板块就够：主卡（一个精选位）→ 最新文字 → 最近更新（跨类型墨底区）；
3. 撤掉后「最新文字」独占整行，5 条能铺得更舒展，不用再被左边栏高度牵着走。

如果主人希望首页仍有「项目露出」，替代做法是**把最新文字从 5 条加到 7 条**，并在首屏内容墙的项目格上显示「最新：Ties」——这个机制现在已经在跑（`wall-cell-tag` 就是干这个的）。

## 2. 搜索：独立 `/search/` 页

### 2.1 为什么独立页

| 维度 | 弹窗（现状） | 独立页 |
|---|---|---|
| 移动端 | 局促，结果被键盘压掉一半 | 全屏可用 |
| 深链 | 做不到（打不开某个搜索结果） | `?q=深圳` 可直接分享 |
| 结果量 | 一个弹窗塞不下 30 条分组结果 | 无压力 |
| 可维护 | 与主题原脚本纠缠 | 一套逻辑一个文件 |

### 2.2 页面构成

```
/search/                          ← 静态壳，无结果时就是空态
┌──────────────────────────────────────┐
│ 搜索                                  │
│ ┌──────────────────────────────────┐ │
│ │ 输入框（等宽字体，2px 墨色底线）   │ │
│ └──────────────────────────────────┘ │
│ [全部] [文章] [城市] [榜单] [生肖]     │ ← 类型 chip
│ [节日] [节假日]                       │
│                                      │
│ 找到 12 条 · 关键词「深圳」           │
│ ─────────────────────────────────    │
│ 深圳                     城市        │
│ 广东省 · 地级市 · 档案 12 项 · 上榜 4 次│
│ ─────────────────────────────────    │
│ 人口大市                榜单          │
│ 第 4 名 深圳 · 按 2025 年末常住人口…  │
└──────────────────────────────────────┘
```

- 结果行左边是标题（命中词高亮 `.search-word`），右边是类型标签，下面一行是摘要。
- 空态：「没有找到「xxx」。可以试试城市名、生肖名或年份。」
- `?q=` 参数支持直达，别人分享链接能直接看到结果。

### 2.3 索引

沿用上一版的技术方案，只改落点：新增 `search-index.js` 生成器输出 `/search-index.json`，收录 article / page / city / province / rank / zodiac / festival / holiday 八类，约 620 条、70–90KB（gzip 后 25–35KB）。

字段统一成 `{ t: 标题, u: 路径, c: 类型, s: 摘要, k: 别名 }`，城市与生肖带拼音别名，搜 `shenzhen` 也能出深圳。

### 2.4 弹窗留不留

| 方案 | 做法 | 代价 |
|---|---|---|
| **① 只留独立页（推荐）** | 导航的搜索按钮直接跳 `/search/`；删掉 `_partials/search.ejs` 与 `local-search.js` 的调用 | DESIGN-LANGUAGE §5.9「搜索弹窗」整节要改成「搜索页」规范；主题原脚本要断干净，不能留半截 |
| ② 两个都留 | 弹窗做快捷查（≤10 条），`/search/` 做完整页 | 两套检索逻辑要同步维护，改一处漏一处是迟早的事 |

推荐 ①，理由是「一个功能一套代码」，站点本来就没有必须要弹窗的理由。但这条动到主题既有结构，要主人明确同意。

## 4. 城市卡片是什么意思（回答主人的疑问）

### 4.1 「数据卡」= 卡面用数据填，不用照片

因为现在只有**一张**城市授权照片（上海，`cityphotos.yml` 实测 1 条）。431 座城市大部分没有图，如果做成图片卡墙，会出现 430 个空框——那比现在的文字列表更难看。

所以卡面用数据填：

```
┌───────────────────────────────┐
│ 深圳            广东 · 地级市  │
│                               │
│ 档案 12 项 · 上榜 4 次          │
│ GDP 3.68 万亿 · 常住 1798 万人  │
└───────────────────────────────┘
```

- 第一行：城市名 + 省级行政区 + 行政级别；
- 第二行：档案厚度（该城已采集多少项指标）+ 上榜次数；
- 第三行：两个最核心的数值（有就显示，没有就不显示这一行，**绝不写估算值**）。

有照片的城市（目前只有上海）以后可以升级成「上图下数据」的图文卡，没图的照旧，不做占位图。

### 4.2 「分省折叠」——这个词我用得不好，说人话就是「这么长的列表怎么摆」

431 张卡一次铺开会很长，手机要滑很久。两种摆法：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲（推荐）** | 全部平铺，**按省分节**，顶部一排省份锚点（点「广东」跳到广东那节） | 无 JS、搜索引擎能抓全、结构简单 | 页面很长 |
| 乙 | 默认只展开上榜最多的 30 城，其余按省折叠，点省展开 | 首屏短 | 需要 JS；折叠内容搜索引擎可能抓不到 |

推荐甲。理由是这站一直坚持「零运行时依赖、构建期出静态」，乙要引入新的交互脚本，收益只是「首屏短一点」。

顺带说一句，现在 `/city/` 顶上那排「按省份浏览」的链接已经有了，甲方案就是把下面的内容换成卡片，结构不用新发明。

## 7. 风险

1. **评选机制一旦跑起来，主卡可能很久不换人**（因为顶替门槛高）。这是设计意图，但如果主人希望「至少每月换一次」，需要在闸三加一条「在位超过 N 个月且池内有 ≥2 分差距者，强制让位」的兜底。要不要加，见 D4 的延伸。
2. **撤掉首页那栏后，项目在首页只剩一个入口格**。若主人希望项目在首页仍有较大露出，需要另设板块，不能靠「精选内容」这个名头。
3. **删弹窗动到主题既有结构**，DESIGN-LANGUAGE §5.9 要整节改写，不是删代码那么简单。
4. **431 张卡的页面体积**：约 150KB HTML，全平铺（甲方案）会更长。移动端首屏不受影响（卡在最下面），但整页加载需要留意。
5. 评选台账落在项目根，**不能进 `public/`**，否则等于把内部决策日志公开了。

## 8. 事实与判断的边界

**可验证事实**：现有三处精选的算法与配置位置；`featured` 勾选数为 0；`personal-reflectio` slug 已失效；搜索索引 6 条 / 站内 648 个 HTML；`/city/` 面包屑把城市档案挂在城市排行榜下；`cityphotos.yml` 仅 1 条；`projects.yml` 3 条。

**判断与建议**：三闸机制的具体分值、2 分门槛、E×3 的权重、撤掉首页那栏、搜索页取代弹窗、城市卡按省分节——这些都是设计方案，不是事实，全部等主人拍板。
